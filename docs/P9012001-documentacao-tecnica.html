Resumo executivo

Programa P9012001 é a rotina batch do sistema S9013 — SIAF (Sistema de Informação de Aquisição e Fornecimento) da CHESF que altera ou exclui, por número interno de registro (ISN), cadastros de simulação/cobrança no arquivo Adabas D9013142-13.

Criado em 21/03/2012 (documento SMP-0232/2012) e ajustado em 08/05/2012 (SMP-0405/2012) para ampliar NUMR-DOCM-COBR de 8 para 9 dígitos. O programa valida 16 parâmetros, imprime imagem ANTES e APÓS via relatório R9012001, e só confirma a transação quando o parâmetro EFETIVA vale SIM — permitindo simulação segura (NAO ? BACKOUT).

Valor de negócio: centraliza manutenção pontual de registros de simulação sem depender de atualização online, com trilha de auditoria impressa e modo dry-run. O conhecimento estava concentrado no código e em especialistas; esta documentação reduz risco de manutenção e fundamenta decisões de migração.

Limitação: análise parcial — seis artefatos dependentes não foram fornecidos (ver aviso acima).

Propósito

Conforme cabeçalho (linhas 27–28): «Alterar/Excluir registros via ISN em modo Batch do arquivo D9013142-13».

Objetivos de negócio

  • Corrigir campos de cadastro de simulação/cobrança (tipo/categoria de documento, contrato, CNPJ, parcela, valores, situação, documento de cobrança, data, vistoria IC1) sem regravar o registro inteiro — apenas campos informados (sentinela NULL).
  • Excluir fisicamente um registro identificado pelo ISN.
  • Permitir ensaio (EFETIVA=NAO) com as mesmas validações e relatório, sem persistir a alteração.
  • Gerar evidência impressa do estado anterior e posterior à operação.

Contexto histórico

  • Criação: 21/03/2012 — analista Edvilson F. Silva, programador Alexandre Vidal — documento SMP-0232/2012.
  • Manutenção: 08/05/2012 — Edvilson Silva — SMP-0405/2012 — campo NUMR-DOCM-COBR de N8 para N9 no arquivo D9013142-13.

Fluxo geral (com fluxograma)

Passos textuais

  1. Receber 16 parâmetros via INPUT (linhas 67–83).
  2. Validar todas as condições de entrada; acumular erros em WFL-TEM-ERRO (87–172).
  3. Se houver erro: mensagem de encerramento; STOP (vídeo) ou TERMINATE 133 (batch) (174–182).
  4. Inicializar WTL-IDNF-FILE, WTL-STTS-REGS='ANTES', WTL-USER-RESP=*USER (186–188).
  5. GET D142-13-CADS-SIMU pelo NUMERO-ISN (etiqueta G1.) e imprimir formulário R9012001 (192–193).
  6. Se FUNCAO=EXCLUIR: DELETE (G1.). Se ALTERAR: PERFORM MOVE-CAMPOS-NAO-NULL e UPDATE (G1.) (195–200).
  7. Se EFETIVA=SIM: END TRANSACTION; senão BACKOUT TRANSACTION (201–206).
  8. Marcar status APOS; se exclusão, RESET da view; nova página e reimpressão do formulário (213–220).
  9. END do programa (260).

Saídas

Mensagens de console / sysout

  • Mensagens de erro de validação (uma por regra violada), via WRITE.
  • Mensagem fixa: Processo encerrado devido aos erros encontrados (linha 176).

Relatório

  • Duas impressões do formulário Relatório R9012001 no report 1 (WRITE(1) NOTITLE USING FORM): estado ANTES (193) e APOS (220), com NEWPAGE(1) entre elas.
  • Variáveis de formulário observadas: WTL-IDNF-FILE (D9013142-13), WTL-STTS-REGS (ANTES/APOS), WTL-USER-RESP (*USER) — layout completo depende de R9012001 ausente.
  • Na exclusão, a view é zerada (RESET) antes da imagem APÓS, produzindo formulário “vazio” após a operação.

Efeito em banco

  • UPDATE ou DELETE no registro ISN, efetivado somente com END TRANSACTION quando EFETIVA='SIM'.
  • Código de término batch em erro: 133.

Regras de negócio (narrativa)

Controle operacional

  • A função só pode ser alteração ou exclusão; não há criação de registro neste programa.
  • O registro-alvo é sempre endereçado pelo ISN — pressupõe-se que o operador já conhece o número interno.
  • A efetivação é explícita: só grava com confirmação SIM. Isso habilita uso como simulação/auditoria prévia.

Atualização parcial

  • Campos de negócio usam a sentinela textual NULL para «manter valor atual».
  • Na alteração, apenas campos ? NULL são movidos para a view antes do UPDATE.
  • Na exclusão, os parâmetros L001-* de conteúdo não influenciam o DELETE (são irrelevantes à operação, embora ainda possam ser validados se ? NULL).

Domínios de código

  • Tipos de documento de simulação e de cobrança: conjunto {00, 02, 04}.
  • Categoria de documento de simulação: {B, R}.
  • Indicador de vistoria IC1: intervalo fechado 00–19.
  • Situação de simulação: deve existir no cadastro acessado por N9013Q06 (retorno 0).
  • Data de documento de cobrança: aceita NULL, zeros ou data válida YYYYMMDD.

Auditoria

  • Sempre imprime imagem antes da mudança; depois imprime imagem após (ou em branco no DELETE).
  • Identifica arquivo, status e usuário no contexto do formulário.

Tratamento de erros

Erros de validação de entrada

  • Modelo: acumular (WFL-TEM-ERRO) + listar todas as mensagens + encerrar.
  • Não há retomada nem correção interativa após o bloco de validação.

Erros de runtime Adabas / Natural

  • Não existe bloco ON ERROR neste fonte.
  • Falha de GET (ISN inexistente), conflito de atualização ou erro Adabas propagam o comportamento padrão do Natural (não documentável sem ambiente).

Performance

  • Complexidade: O(1) por execução — um único GET por ISN, no máximo um UPDATE ou DELETE, uma chamada CALLNAT condicional, duas impressões de formulário.
  • Acesso por ISN: leitura direta posicional; não há laço nem pesquisa por descritor — excelente para manutenção pontual, inadequado como varredura em massa.
  • CALLNAT: custo adicional apenas quando L001-INDC-SITC-SIMU ? 'NULL'; frequência depende do uso operacional.
  • Transação curta: uma unidade de trabalho Adabas por execução — baixo risco de hold prolongado, desde que o programa não fique parado entre GET e END TRANSACTION em sessão interativa.
  • Relatório: duas escritas de formulário; impacto depende do destino do report 1 (spool), não do banco.

Não há evidência de buffer pooling customizado, prefetch ou processamento multi-registro neste objeto.

Sugestões de modernização

Escopo desta história: apenas consultivo — nenhuma migração foi implementada.

Separação de responsabilidades

  • Extrair validações (RN-01–RN-16) para um módulo/serviço de domínio reutilizável, independente de Natural INPUT.
  • Isolar acesso a dados (GET/UPDATE/DELETE + transação) em repositório Adabas ou, na migração, em API de persistência.
  • Tratar relatório de auditoria como evento/log estruturado (JSON/PDF) em vez de FORM acoplado.

Exposição como serviço

  • API REST (ex.: PATCH /simulacoes/{isn}, DELETE /simulacoes/{isn}) com corpo parcial (equivalente ao NULL) e query/header efetiva=true|false.
  • Implementação candidata: Java / Quarkus (ou Spring) com bean de validação Bean Validation + serviço de aplicação transacional.
  • Substituir CALLNAT N9013Q06 por consulta a tabela/serviço de domínio de situações.

Riscos da migração

  • Sem DDM e sem N9013Q06/R9012001, há risco de mapear mal tipos numéricos (N15,2), datas e layout de auditoria.
  • Semântica de VAL() e máscaras Natural pode divergir de parsers Java.
  • Jobs JCL que dependem do código de retorno 133 precisam de contrato equivalente HTTP/batch.
  • ISN Adabas não deve vazar como identificador de negócio na API pública — preferir chave de negócio estável, se existir no arquivo (a confirmar na FDT).

Caminho recomendado (fases)

  1. Completar pacote de artefatos ausentes e fechar o modelo de dados.
  2. Testes de caracterização (golden files) do programa atual com EFETIVA=NAO e SIM.
  3. Reimplementar validações + persistência em serviço; manter Natural como fachada temporária (strangler).
  4. Migrar consumidores batch/online; desativar P9012001.
