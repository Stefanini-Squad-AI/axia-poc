    5. Análise de Impacto de Mudanças

    Metodologia

    Para avaliar o impacto de uma alteração em um programa ou objeto, use o seguinte fluxo:

    1. Identifique o programa/objeto que será alterado
    2. Consulte o Mapa de Dependências para ver quem depende deste programa/objeto
    3. Para cada dependente:
      • Leia a documentação completa do programa
      • Identifique como o programa usa o objeto alterado
      • Determine se a alteração quebra funcionalidade ou modifica comportamento
    4. Consulte Regras de Negócio e Riscos para cada programa afetado
    5. Documente o impacto em relatório de análise antes de executar a mudança

    Cenários de Impacto Comum

    Tipo de Mudança Objetos Afetados Análise Necessária Risco
    Alterar campo em arquivo Adabas Arquivo + todos os programas que acessam Todas as seções "Inventário de Objetos" e "CRUD Matrix" 🔴 Alto
    Alterar LDA (estrutura de dados) LDA + todos os programas que usam LOCAL USING Seções "Mapa de Dependências" e "Problemas e Riscos" 🔴 Alto
    Alterar programa chamado (CALLNAT) Programa chamado + todos os callers Seção "Grafo de Chamadas" de cada caller 🟡 Médio
    Alterar regra de validação Programa + possíveis dependentes de dados Seção "Regras de Negócio" e "Mapa de Impacto" 🟡 Médio

    Exemplo Prático: Alterar P9012001

    ⚠️ Análise de Impacto: Se P9012001 for alterado:
    1. Dependências diretas afetadas: Nenhum programa no repositório depende de P9012001
    2. Objetos alterados potencialmente: D9013142-13 (se lógica de UPDATE/DELETE mudar)
    3. Risco operacional: Qualquer programa que acessa D9013142-13 pode ser afetado (não identificado no repositório atual)
    4. Validações afetadas: Se regras de negócio (BR-001 a BR-027) forem alteradas, dados podem ser aceitos/rejeitados de forma diferente

    7. Padrões de Documentação

    Estrutura de 14 Seções

    Cada programa é documentado em 14 seções padronizadas, conforme descrição abaixo. Esta padronização permite comparação direta entre programas:

    Seção Propósito Público-Alvo Quando Usar
    1. Resumo Executivo Visão de alto nível: o quê, quem, quando Gerentes, Analistas Primeira leitura; decisões de impacto
    2. Resumo Técnico Plataforma, linguagem, métricas de código Arquitetos, Analistas Técnicos Avaliação de modernização
    3. Fluxo de Execução Passo-a-passo do programa Programadores, QA Compreender lógica; testes
    4. Inventário de Objetos Lista completa de objetos usados Analistas, DBA Rastrear dependências; localizar código
    5. Mapa de Dependências Quem/o quê o programa depende Analistas de Impacto Análise de mudança (programa → mundo)
    6. Grafo de Chamadas Profundidade de chamadas; cadeia de dependências Programadores, Analistas Entender cascata de falhas
    7. Matriz CRUD Operações (Create, Read, Update, Delete) por tabela/arquivo DBA, Analistas de Dados Análise de integridade; replicação
    8. Mapa de Impacto Quem depende deste programa Analistas de Impacto Análise de mudança (mundo → programa)
    9. Regras de Negócio Validações, decisões; BR-001, BR-002, etc. Analistas de Negócio, Compliance Verificar regras antes de alterar
    10. Performance Operações críticas; gargalos; escalabilidade Arquitetos, Analistas de Performance Otimização; planejamento de capacidade
    11. Problemas e Riscos Bugs conhecidos; riscos operacionais; segurança Todos (referência rápida) Antes de executar em produção
    12. Refatoração Oportunidades de melhoria técnica Arquitetos, Programadores Planejamento de modernização
    13. Estratégia de Modernização Candidatura para refactor; roadmap; ROI Gestores, Arquitetos Decisões de investimento em tecnologia
    14. Artefatos Ausentes Limitações da análise; grau de confiança Todos (transparência de risco) Antes de tomada de decisão crítica

    Como Adicionar Novo Programa

    Quando um novo programa for adicionado ao repositório `Codigo-natural/`, execute os seguintes passos:

    1. Analise o arquivo `.NSP` do programa
    2. Crie novo arquivo HTML `<PROGRAMA>-Documentation.html` (exemplo: P9012002-Documentation.html) usando P9012001-Documentation.html como template
    3. Preencha todas as 14 seções com informações específicas do novo programa
    4. Adicione uma linha na tabela de programas desta REPOSITORY-OVERVIEW.html
    5. Atualize o Mapa de Dependências Consolidado com as dependências do novo programa
    6. Identifique objetos compartilhados e atualize a seção "Mapa de Objetos Compartilhados"
    7. Revise análise de impacto e atualize "Mapa de Impacto (Dependências Inversas)" de todos os programas afetados

    Convenções de Nomenclatura

    • Programas: `P<número>` (ex: P9012001, P9012002)
    • Documentação: `<PROGRAMA>-Documentation.html` na raiz do repositório
    • Arquivos de Código: `Codigo-natural/<ARQUIVO>.NSP`
    • LDAs: `L<número>` (Local Data Area) ou `A<número>` (shared LDA)
    • Formulários: `R<número>` (Report/Formulário)
    • Arquivos Adabas: `D<número>` (Data file)

    9. Manutenção da Documentação

    Quando Atualizar a Documentação

    • Alteração de programa: Atualizar seções 3 (Fluxo), 9 (Regras), 11 (Riscos)
    • Adição de nova dependência: Atualizar seção 5 (Dependências) e 8 (Impacto)
    • Adição de novo programa ao repositório: Criar nova documentação de 14 seções + atualizar índice
    • Recuperação de artefato ausente: Atualizar seção 14 (Artefatos Ausentes) de todos os programas afetados
    • Mudança de ambiente (Adabas versão, etc): Atualizar seção 2 (Resumo Técnico) e 10 (Performance)

    Responsabilidades

    • Programador: Mantém código atualizado no repositório
    • Analista Técnico: Atualiza documentação quando código muda (seções 1-6)
    • Analista de Negócio: Atualiza regras de negócio (seção 9)
    • Arquiteto: Atualiza estratégia de modernização (seção 13)
    • QA/DBA: Atualiza CRUD matrix, performance, riscos (seções 7, 10, 11)

    Processamento de Alteração Exemplo

    Se uma alteração SMP (ex: SMP-0406/2025) for autorizada para P9012001:

    1. Programador executa alteração no código e commit no repositório
    2. Programador atualiza comentários do código com novo número SMP
    3. Analista Técnico revisa alteração e atualiza P9012001-Documentation.html:
      • Seção 3: Fluxo (se lógica mudou)
      • Seção 4: Inventário de Objetos (se dependências mudaram)
      • Seção 5: Mapa de Dependências (se novos objetos usados)
      • Seção 9: Regras de Negócio (se validações mudaram)
      • Seção 11: Problemas e Riscos (se novos riscos identificados)
    4. Gestor atualiza REPOSITORY-OVERVIEW.html com data de última alteração
    5. Documentação revisada é validada antes de merge
